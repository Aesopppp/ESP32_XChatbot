# ESP-VoCat / ACOS 中文源码阅读指南

本文对应当前 ESP-VoCat v1.2 工程。源码中的中文注释侧重说明设计原因、
数据流、对象所有权、线程限制和容易误解的边界。代码及当前编译配置是
实际行为的依据；以后修改参数时，应同时更新相关注释和本文。

## 1. 工程目录与注释范围

| 位置 | 用途 | 开发时如何处理 |
| --- | --- | --- |
| `main/` | 设备固件的应用源码 | 修改功能的主要位置 |
| `main/boards/espressif/esp-vocat/` | VoCat 硬件初始化与引脚 | 硬件相关修改先看这里 |
| `main/boards/common/` | 通用板级接口、联网、背光等 | 多种板型共用，修改须考虑其他板型 |
| `main/audio/` | 采集、AFE、唤醒、编解码和播放 | 音频实时路径，避免阻塞与无限缓存 |
| `main/protocols/` | ACOS 与小智协议适配 | 当前业务主要使用 ACOS |
| `main/display/` | 屏幕、状态图标、表情 | VoCat 当前使用表情显示实现 |
| `main/notify/` | HTTP 音频通知播放 | 与对话共用音频播放服务 |
| `scripts/`、`tools/` | 构建、资源准备、本机配置与验证 | 脚本在电脑执行，不在设备上执行 |
| `docs/`、根目录中文指南 | 架构、协议与操作说明 | 配合源码阅读 |
| `managed_components/`、`components/` | 下载或随工程提供的依赖组件 | 不手工修改下载/供应商代码 |
| `build/`、`releases/` | 编译及发布产物 | 由工具生成，不作为功能修改入口 |
| `sdkconfig*`、语言及 mmap 生成头文件 | 配置或生成结果 | 使用 menuconfig/资源生成工具管理 |

这次注释覆盖 VoCat 实际运行路径，以及相关公共模块、协议和资源脚本。
上游其他开发板、第三方依赖、二进制图片与模型没有逐个重写注释。
例如 ESP32-C3 板型源码虽然当前没有编译，仍属于上游多板型工程的一部分。

## 2. 推荐阅读顺序

1. `main/main.cc`：找到固件启动入口。
2. `main/application.h` 与 `main/application.cc`：理解应用主循环和事件。
3. `main/device_state.h` 与 `main/device_state_machine.cc`：理解运行状态。
4. `main/boards/espressif/esp-vocat/esp_vocat.cc`：理解实际硬件。
5. `main/protocols/acos_protocol.h` 与 `.cc`：理解 ACOS 数据收发。
6. `main/audio/audio_service.h` 与 `.cc`：理解音频队列与工作任务。
7. `main/audio/engines/afe_audio_engine.cc`：理解 AEC、VAD 和唤醒。
8. `main/display/emote_display.cc`：理解屏幕状态和图标资源。

## 3. 从上电到等待唤醒

`app_main()` 首先初始化 NVS，再初始化并运行 `Application`。
NVS 是断电后仍保留设置的 Flash 存储。遇到特定 NVS 初始化错误时，
启动入口会擦除并重建 NVS，此时已保存设置可能丢失。

`Board::GetInstance()` 提供当前唯一板型实例，板型通过 `DECLARE_BOARD`
工厂注册。一次构建只能有一个有效板级工厂。应用层依赖 `Board` 接口，
不直接引用具体 VoCat 类或它的引脚配置。

VoCat 构造过程初始化 I2C、识别 PCB 与供电状态，再初始化外设、显示和输入。
音频 codec 由板级接口提供，稍后交给音频服务使用。硬件 v1.0 和 v1.2 的
差异由当前识别逻辑处理，不能随意把其他板子的引脚写进公共应用层。

联网后，ACOS 传输在后台建立 WebSocket 并鉴权。当前 ACOS 路径绕过
小智服务的激活/配置发现流程，也不把小智 MCP 消息直接发给 ACOS。
Wi-Fi 连上、WebSocket 鉴权成功、会话被唤醒是三个不同条件：
即使网络已就绪，仍需本地唤醒才能开始上传用户声音。

当前唤醒词是“你好小益”（“你好小易”同音），对应模型
`wn9_nihaoxiaoyi_tts2`。模型决定可识别的词语，改日志或屏幕文案不会
产生新唤醒词；更换词语必须选择或取得相应语音模型，并重新构建资源。

## 4. 应用状态、连续对话与打断

应用状态由 `Application::SetDeviceState()` 和状态机统一管理。
界面、监听和播放随状态及协议事件变化；网络回调、音频回调不应直接
随意改变应用状态，应使用 `Schedule()` 或事件位交给应用主循环处理。

首次唤醒打开的是会话的音频上传门，不是临时新建一个 WebSocket。
进入对话后，麦克风处理与上传持续运行，因此下一句话无需重新唤醒。
空闲检查在监听状态、播放已经空闲且输入时间有效时执行；无输入约
60 秒后关闭会话上传，回到待唤醒。回答播放中不会仅因计时到点就休眠。

讲话打断依赖持续上传的 AEC 处理音频，以及服务器确认的
`speech_started` 事件。本地 VAD 用于语音活动信息，不能把残余回声的
一次 VAD 上升直接等同于用户主动打断。

打断时同时处理两个边界：

- 网络边界：标记旧回答不可接受，必要时发送 `response.cancel`，
  丢弃仍在网络中传来的旧尾包，等待服务器结束/取消确认及用户说完。
- 播放边界：清空待解码与待播放队列，增加播放代次，让正在处理的旧结果失效。

麦克风上传不随清除下行播放队列而停止，因此能保留打断句的句首。
已经交给 I2S/DMA 的很短尾音不一定能被软件清队列立即撤回。

`acos_response_flow.h` 管理回答编号、取消屏障和用户讲话结束门。
当前二进制音频没有逐包 `response_id`，所以必须谨慎维护这些边界。
不能只清一次缓存就立即接受任意后续二进制帧，否则旧回答可能重新播出来。

## 5. 上行：从麦克风到 ACOS

数据路径：

```text
ES7210 / I2S 采集
  -> AFE（回声消除、语音活动检测等）
  -> PCM 编码队列
  -> Opus 编码
  -> 音频发送队列
  -> ACOS JSON 排队
  -> WebSocket 后台发送
```

当前网络上行是 16 kHz、单声道、16 位 PCM 对应的 20 ms Opus 帧。
`SendAudio()` 把压缩音频 Base64 编码，封装为
`input_audio_buffer.append` JSON，然后排队。网络发送由协议后台线程完成，
不在采集任务或应用主循环中同步等待网络写入。

AFE 输出的连续 PCM 包括静音帧，不能只上传本地 VAD 判定为人声的帧：
云端需要连续时间轴判定句子起止，截掉静音或起始帧可能破坏识别和打断。
编码器开启 DTX/VBR 等参数，静音上传不代表每一帧都占用相同字节数。

离线时 `SendAudio()` 返回成功表示当前包已被消费或丢弃，并不证明
服务器已经收到。上传队列有容量、会话代次和年龄限制，恢复连接后
不会把断网期间积压的旧声音全部补发。

## 6. 下行：从 WebSocket 到扬声器

数据路径：

```text
WebSocket 二进制 Opus / JSON 控制事件
  -> ACOS 接收队列
  -> 主循环 Poll 按顺序投递
  -> Opus 解码及重采样
  -> PCM 播放队列
  -> ES8311 / I2S
  -> 功放和扬声器
```

当前 ACOS 服务下行约定为 16 kHz、60 ms 二进制 Opus 帧。
VoCat 硬件音频采样率为 24 kHz，音频服务负责必要的重采样。
上下行帧时长不同，不能用上行 20 ms 假设计算全部下行缓存的实际时长。

接收回调只做校验、控制识别和入队，不解码、不等扬声器播完。
`Poll()` 在应用主循环中释放音频，保持控制事件与音频的接收顺序。
服务器的 `response_done` 表示传输边界结束，不表示扬声器已经播完。

`acos_audio_policy.h` 的预缓冲目标是约 300 ms，逻辑等待上限约 600 ms；
实际释放仍取决于主循环调度和下游可用空间。短句在结束事件到达后可
提前播放。已播放后下游耗尽会重新预缓冲，避免每收到一个包就播放一次。
这能缓解网络抖动，无法保证网络长时间断流时仍连续出声。

普通对话音频在内存队列中流式解码播放，没有因此自动保存成 SD 卡文件。
增加录音备份需要独立文件写入路径，不能直接在实时回调里慢速写卡。

## 7. AFE、AEC 与扬声器参考

`afe_audio_engine.cc` 创建和驱动 ESP-SR AFE。VoCat 的 codec 实现位于
`audio/codecs/box_audio_codec.cc`：ES7210 用于采集，ES8311 用于输出。
RX 使用 TDM 槽位，物理麦克风通道和软件槽位不是同一个概念。

逻辑输入格式 `MR` 表示麦克风和扬声器参考，R 不是第二个人声麦克风。
AEC 利用参考估计并抑制扬声器回声；输入增益与参考增益分别管理。
仅打开 AEC 配置不能保证任何音量、距离和环境下都不会残留回声。

AFE 的启停、重置由拥有 AFE 的处理任务执行。其他任务设置待处理标志，
由该任务在安全边界应用，避免 Feed/Fetch 与模型重置并发破坏内部状态。
模型可能借用挂载资源中的内存，也可能由回退加载路径拥有；资源卸载时
必须遵守其生命周期，不能把旧模型指针继续交给运行中的处理器。

唤醒音频缓存可保存约 2 秒 PCM，用于需要上传唤醒前音频的协议。
当前 ACOS 不上传该唤醒缓存；连续对话打断的句首来自持续的处理与上行。

## 8. 缓存、任务与锁

| 缓存 | 当前限制 | 说明 |
| --- | --- | --- |
| PCM 编码队列 | 2 帧 | 避免未压缩音频大量积压 |
| PCM 播放队列 | 2 帧 | 扬声器前的小队列 |
| 普通解码队列 | 按 `1200 / OPUS_FRAME_DURATION_MS` 限包数 | 宏按协议上行帧时长计算，实际下行总时长依包时长 |
| 音频发送队列 | 按 2400 ms 上行帧数限制 | ACOS 上行为 20 ms |
| ACOS JSON 上传队列 | 50 个消息 | 音频消息约 1 秒，过期消息丢弃 |
| ACOS 接收队列 | 512 KiB 或 2048 帧 | 字节数与帧数独立约束，任一触顶均受限 |
| 测试录音队列 | 按 10 秒帧数预留 | 解码队列实际存储容量也匹配，方便交换 |

队列容量不是当前已占用内存。压缩帧长、当前流量、预分配槽位、PCM
缓存、任务栈和模型都影响内存占用；应结合设备日志中的内部堆与 PSRAM
余量判断，而不能只把上述时长相加。

音频输入、输出、Opus 处理和 AFE 处理在各自任务运行。ACOS 后台线程
负责发送、心跳、重连和取消。应用主循环处理状态和协议 Poll。
音频队列锁保护队列、处理中标志和播放代次；耗时 I/O 与编解码尽量
在锁外完成。解码器和输入重采样器另有互斥保护。

软件播放耗尽条件包含队列为空和没有正在解码/输出的任务，仍不等同于
硬件 DMA 无尾音。`HasFreshVoiceInput()` 只检查最近是否收到处理帧，
不是“有人说话”；判断人声应看 VAD。

## 9. 网络、设置、显示与通知

`wifi_board.cc` 先尝试已保存网络，没有网络或连接超时后进入配网。
热点配网页面由 Wi-Fi 依赖组件提供，固件桥接状态与界面。
本机可通过 `.local/wifi.json` 预置网络；不应把实际密码写进公共源码。

`settings.cc` 封装 NVS 的命名空间、默认值和读写。
Set 接口置脏标志，对象析构时提交。当前删除接口没有同样置脏标志，
阅读或新增调用时不能想当然地认为其提交行为完全相同。
NVS 键名是持久化接口，重命名需要考虑已有设备的数据迁移。

`emote_display.cc` 将状态映射到表情系统的事件和图标。播放图标的像素
来自资源文件，不是状态名称生成的。`assets.cc` 管理模型与显示资源的
挂载、索引与更新；挂载资源的指针不能跨卸载继续使用。

`notify_player.cc` 从 HTTP 分块读取 Ogg/Opus 音频，交给共用解码队列。
字幕按播放媒体时间推进；通知完成需要下载结束且播放耗尽。
这不是本地定时提醒引擎，也不会把任意文字自动转换为语音。

`mcp_server.cc` 提供小智设备工具的结构化参数与分发，使用调度机制执行
应用操作。ACOS 当前不声明兼容小智 MCP，不能仅发送同名 JSON 就认为
设备工具已经接通。`ota.cc` 管理固件升级；资源升级属于另一路径。

## 10. 配置和资源构建

- `main/Kconfig.projbuild`：menuconfig 中的板型、协议和音频功能选项。
- `main/CMakeLists.txt`：选择源文件、板型、语言、依赖和生成资源。
- `tools/generate_acos_config.py`：本机 ACOS JSON 转成构建目录中的头文件。
- `tools/generate_wifi_config.py`：本机 Wi-Fi JSON 转成构建默认值。
- `scripts/prepare_vocat_wake_assets.py`：按 sdkconfig 为 VoCat 重打包唤醒模型。
- `scripts/prepare_vocat_speaker_icon.py`：替换播放图标右侧声波并生成预览。

本机凭证文件被 Git 忽略，但编译进设备的默认配置仍存在于固件里。
协议读取 NVS 中的 ACOS 值优先于本机编译默认值，排查服务器配置时要
同时考虑 NVS 覆盖，不能只检查生成头文件。

当前播放图标为 30×30 的 RGB565A8 资源：12 字节头部、1800 字节颜色、
900 字节透明度。现有脚本保持左侧喇叭，替换右侧两道声波。
普通 PNG 不能直接改扩展名当成设备图标，需要使用相应编码与打包流程。

## 11. 常用修改入口与验证

| 希望修改 | 优先阅读的位置 |
| --- | --- |
| 开机音量或按键音量行为 | `esp_vocat.cc`、`box_audio_codec.cc` |
| 闲置后重新需要唤醒的时间 | `application.cc` 的 ACOS 空闲检查 |
| 唤醒词 | 板型构建配置、Kconfig、唤醒资源准备脚本 |
| 回答预缓冲与欠载策略 | `acos_audio_policy.h`、`acos_protocol.cc` |
| 打断取消与旧音频过滤 | `acos_response_flow.h`、协议与应用中断路径 |
| AEC、参考通道、采集增益 | `afe_audio_engine.cc`、`box_audio_codec.cc` |
| 表情和状态图标 | `emote_display.cc`、图标准备脚本及资源 |
| ACOS 地址和鉴权 | 本机配置生成器、`AcosProtocol::Start()` |

当前工程使用 ESP-IDF 6.1，不支持 5.x。保留现有 menuconfig 的增量编译：

```powershell
cd D:\ESP32_XChatbot_v1.2
. .\tools\enter-idf.ps1
idf.py build
```

`tools/dev.ps1 build` 调用变体构建，会重新生成 sdkconfig，适用于初始化
或恢复默认板型配置；日常修改不要把它当作一定保留 menuconfig 的入口。

修改功能后，固件编译和主机检查只能验证一部分行为。涉及音频、网络、
打断或硬件时，还应在设备上验证唤醒、完整回答、连续追问、短句打断、
恢复联网及一分钟空闲。仅修改注释和文档无需为了生效重新烧录设备。
